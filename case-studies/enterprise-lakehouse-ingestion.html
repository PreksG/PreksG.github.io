Enterprise Lakehouse & Ingestion Architecture

The metadata-driven ingestion pattern behind several of my pipelines: Azure Data Factory lands source databases in ADLS Gen2, and Databricks notebooks move the data through landing, Silver and Gold workspaces in Microsoft Fabric.

01 Overview

Project overview

One ingestion pattern, used across several sources: a Lookup decides which tables to load at run time, a ForEach copies each one into ADLS Gen2, and Databricks notebooks move the data through landing, Silver and Gold workspaces in Microsoft Fabric.

02 Context

Business context

Several sources feed the group's analytics: an on-premises database behind the annuitant biometrics application, the group's digital quoting app, the legacy general and life ledgers, and the intermediary web portal used by brokers and agents. Each is a SQL database whose tables change over time.

03 Problem

Problem statement

Copying these sources one table at a time does not scale:

  • Tables change over time, so a hand-maintained table list keeps breaking.
  • Hardcoding each table in a pipeline means a pipeline change every time the scope changes.
  • Reruns must not duplicate data that has already landed.

04 Architecture

Solution architecture

Source database → Lookup decides which tables to load at run time → ForEach copies each table → ADLS Gen2 → Databricks notebooks → landing workspace → Silver → Gold (Microsoft Fabric)

06 Implementation

Implementation approach

Four ways to decide what to load

  • System catalogue: a Lookup reads the current table list from the database itself, so new tables are picked up automatically.
  • Information schema: a Lookup returns only the in-scope tables.
  • Control table: a table in Azure SQL lists what to copy, so adding a table is a row change, not a pipeline change.
  • Pipeline variable: an array maps each source table to its sink folder.

Worked example: annuitant biometrics database replication

The annuitant biometrics application kept its data in an on-premises SQL Server database, out of reach of the analytics platform, and its tables changed over time. A master pipeline runs three steps in order:

  • Application schema: a Lookup reads the current table list from the system catalogue, and a ForEach copies every table to Parquet in ADLS Gen2, one file per table.
  • Background-job schema: the same discover-then-copy pattern for the application's job-scheduler tables.
  • Push to Fabric: a Databricks notebook loads the landed files into the Fabric workspaces.
  • Outcome: the annuitant data refreshed on schedule into the lakehouse with no manual table upkeep.

Worked example: digital quote platform ingestion

Quotes from the group's digital quoting app (the product list, quotes, quoting clients, and vehicle and travel quotes) sat in the app's SQL database, so nobody could analyse quote volumes or conversion.

  • Version 1: a single Copy activity moved the vehicle-quote table from SQL Server to ADLS Gen2 as delimited text.
  • Version 2: a Lookup on the information schema returns the five in-scope tables, a ForEach copies each to ADLS Gen2, and two Databricks notebooks promote the data from the landing workspace to Silver.
  • Outcome: quote data landed and cleaned in Silver, ready for quote-to-policy reporting. The pipeline has since been archived.

The same pattern elsewhere

  • The legacy-ledger full dumps: the "before" step of the GL crosswalk.
  • The intermediary-portal pipelines: the ingestion side of the sales-to-revenue pipeline.

07 Data quality

Data quality and validation

  • Tables discovered at run time, so a new table is not silently missed.
  • Delete-before-copy on the portal's life pipeline, so reruns never duplicate data.
  • Table names escaped in the dynamic SQL used for the ledger dumps.
  • One file per table, named after the table, so every landed file traces back to its source.

08 Results

Results and business impact

Source databases refreshed on schedule into the lakehouse with no manual table upkeep.

  • A change of scope is a metadata change, not a pipeline rebuild.
  • Several of these feeds supply the group client view, the GL crosswalk and the cross-sell analytics.

Measured impact: not yet quantified. No revenue, time-saving or accuracy figures are claimed. Company names, real figures and internal rules are withheld.
