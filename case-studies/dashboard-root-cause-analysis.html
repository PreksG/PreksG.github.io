Dashboard Root-Cause Analysis

Finding out why a dashboard's numbers are wrong, and fixing the cause at the right layer, not the symptom in the report.

01 Overview

Project overview

A series of investigations that traced wrong, missing and inflated dashboard figures back to their real causes in the warehouse, the data model, the DAX or the source process, then fixed them or handed a precise diagnosis to the team that owned the layer.

02 Context

Business context

Business teams relied on Power BI dashboards for sales, lending, operations and compliance. When figures were wrong, trust in every dashboard suffered.

03 Problem

Problem statement

The symptoms varied:

  • Historical data missing from a dashboard.
  • Several measures returning identical values when they should differ.
  • Two dashboards disagreeing on the same count.
  • User counts far higher than the web-analytics source.
  • A dashboard crashing repeatedly, and a compliance report showing outdated status.

04 Objectives

Objectives

  1. Reproduce each reported problem and confirm it is real.
  2. Find the root cause, wherever it sits in the pipeline.
  3. Fix the cause at the correct layer, or hand a precise diagnosis to its owner.
  4. Verify the fix against an independent source.
  5. Explain findings and next steps to stakeholders clearly.

05 My role

My role and contribution

I carried out these investigations as a BI analyst and analytics engineer. Upstream table rebuilds were carried out by data engineering colleagues, using my diagnoses.

  • Reproduced each problem and found its root cause.
  • Fixed BI-layer causes directly, including a connector migration and a regional filter.
  • Wrote root-cause documents and technical bug reports for data engineering.
  • Drafted stakeholder communications explaining each finding in plain language.

06 Architecture

Solution architecture

Symptom → reproduce → compare with an independent source → trace lineage layer by layer → isolate the cause → fix at the right layer (or hand off) → verify → explain to stakeholders

08 Implementation

Implementation approach

  • Reproduce and confirm exactly what is wrong, for which period and which slice.
  • Compare with a trusted source, such as web analytics, a source system or another dashboard.
  • Walk back from the visual through the measure, the model, the warehouse tables and the source until the figure changes.
  • Fix BI-layer problems directly; send upstream problems to data engineering with a precise diagnosis and a recommended fix.
  • Verify each fix against the independent source and explain it in plain language.

09 Data quality

Data quality and validation

  • Independent comparison: headline figures reconciled with a trusted source.
  • Grain check before and after each join; distinct-count check per entity.
  • History check: upstream tables cover the full reporting period.
  • Load check: no duplicate rows from appended or chunked loads.
  • Filter check: measures tested with and without filters, especially after interim fixes.
  • Source check: system or manual file, and how fresh it is.

10 Results

Results and business impact

  • Wrong figures found and explained before they drove decisions.
  • Fixes made at the cause, so problems did not return.
  • Clear hand-offs to data engineering, with the evidence needed to act.
  • Stakeholders kept informed in plain language.
  • A repeatable approach that speeds up future investigations.

Measured impact: not yet quantified. No revenue, time-saving or accuracy figures are claimed. Company names, real figures and internal rules are withheld.

11 Lessons

Key lessons and capabilities

When a dashboard shows the wrong number, the visible problem is in the report but the cause is usually upstream. Patching the report hides the problem; it does not solve it.

What this project taught me

  • The symptom is rarely where the cause is: most causes sat upstream of the report.
  • Interim fixes create new problems: one earlier fix introduced a filter conflict that made several measures identical.
  • Distinct counts are not always distinct: a table holding two records per loan overcounted silently.
  • Not every problem is a data problem: one compliance issue came from a stale manual spreadsheet.

Capabilities demonstrated

  • Root-cause analysis
  • DAX and data-model debugging
  • Warehouse lineage tracing
  • Stakeholder communication
